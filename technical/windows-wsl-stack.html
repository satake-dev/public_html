Ambiente de Desenvolvimento: Windows + WSL

Este é um exemplo de ambiente Windows + WSL para manter fluxo Linux no desenvolvimento, sem abrir mão da interface principal no Windows.

Por muitos anos, Linux em dual boot com Windows foi uma abordagem comum para desenvolvimento. Com a maturidade do WSL, tornou-se possível consolidar uma rotina mais fluida: Linux para build e execução, Windows para produtividade de desktop.

1) Contexto histórico: dual boot por muitos anos

Durante boa parte da carreira, a forma mais confiável para desenvolvimento Linux era manter uma partição dedicada e alternar entre sistemas. Funcionava, mas trazia custo operacional: reinícios frequentes, isolamento de arquivos e maior atrito para tarefas rápidas.

2) Evolução para WSL como padrão

Com a evolução do WSL em compatibilidade e performance, é possível manter shell, ferramentas de build e automações no Linux, aproveitando no Windows os recursos que favorecem documentação, navegação e multitarefa.

3) Fluxo atual de trabalho

  • Código e automações rodam no ambiente Linux (WSL).
  • Edição e navegação acontecem com interface principal no Windows.
  • Repositório e scripts seguem padrão Linux para reduzir variação entre ambientes.
  • Validações finais são feitas em browser desktop e mobile antes de publicar.

5) Como abrir o VS Code no WSL

É possível abrir o VS Code diretamente pelo ambiente WSL, mantendo editor, terminal e arquivos no mesmo contexto Linux do projeto. Nesse modelo, o comando code . inicia a sessão já conectada à distribuição, e o status no rodapé do editor indica que a execução está em WSL. Quando esse comando não está disponível, normalmente basta concluir a instalação do VS Code no Windows com a extensão WSL (Remote - WSL) para habilitar esse fluxo.

Por que isso é fundamental

  • Consistência de ambiente: desenvolvimento, build e execução acontecem no mesmo Linux.
  • Menos erros de path e permissões: scripts, git, Docker e kubectl seguem o mesmo padrão Unix.
  • Mais performance de I/O: editar no filesystem Linux evita atritos comuns de integração.
  • Fluxo cloud-native real: AWS, Azure, OCI e Kubernetes ficam no contexto correto desde o início.

6) Boas práticas e limites

  • Uso WSL para desenvolvimento, automação e consistência de ambiente.
  • Uso Windows nativo para ferramentas de escritório e comunicação.
  • Evito misturar caminhos e permissões sem critério entre os dois mundos.
  • Mantenho scripts e processos padronizados para facilitar onboarding e reprodução.

7) Conclusão

Durante muito tempo, desenvolver software em uma mesma máquina significava conviver com dois mundos que não se encontravam naturalmente: o Windows, necessário para a rotina corporativa, comunicação e aplicações de desktop, e o Linux, indispensável para build, automação, containers e previsibilidade de ambiente. O dual boot foi a ponte possível dessa época e, para muita gente, funcionou com mérito; era o método que permitia manter produtividade em contextos diferentes, mesmo com o custo silencioso de interromper o fluxo para reiniciar, trocar de sistema e recuperar contexto toda vez que uma tarefa atravessava fronteiras. Com a maturidade do WSL, essa história ganhou um final melhor: o Linux passou a existir dentro do Windows com consistência real, sem abandonar ferramentas de trabalho, sem a fricção da troca de sistema e sem transformar cada ajuste técnico em logística operacional. O que antes era um ritual de sobrevivência virou um fluxo contínuo de engenharia, em que a energia volta para o que realmente importa: pensar, construir e entregar software.

Dual boot foi heróico no seu tempo, principalmente entre o fim dos anos 2000 e boa parte da década de 2010: dois sistemas, muito contexto e alguns reinícios existenciais. Hoje o roteiro mudou. Com WSL, o Linux roda dentro do Windows sem cerimônia, sem troca de SO e sem a clássica loteria da partição. Resultado: menos logística de ambiente e mais código chegando em produção.
