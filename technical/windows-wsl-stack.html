Ambiente de Desenvolvimento: Windows + WSL

Por muito tempo, trabalhar com Windows e Linux na mesma máquina era quase um esporte: abrir um sistema, perceber que faltava uma ferramenta, reiniciar, abrir o outro, repetir. O dual boot salvou muita gente nessa fase e teve seu mérito, porque permitia usar Windows para a rotina de escritório e Linux para build, automação e ambiente parecido com produção. Só que havia um preço: quebra de foco, troca de contexto e aquela sensação de que metade da energia ia para organizar o ambiente, não para resolver o problema. A virada começou em 2016 com o WSL 1 e ficou madura em 2019 com o WSL 2, trazendo kernel Linux real, mais compatibilidade e um fluxo muito mais estável. Com VS Code integrado ao WSL, Linux e Windows pararam de disputar atenção e começaram a jogar no mesmo time. No fim, a conta fecha simples: menos drama de setup, mais tempo para escrever código que importa.

O dual boot foi o plano A durante anos. Em 2019, com o WSL 2, veio o plano melhor: Linux como base principal de desenvolvimento e execução, com o Windows apoiando o dia a dia, sem aquela ginástica de reiniciar a máquina.

1) Contexto histórico: dual boot por muitos anos

Durante boa parte da carreira, o caminho mais confiável era manter uma partição Linux dedicada e alternar entre sistemas. Funcionava, claro, mas cobrava pedágio: reinícios frequentes, arquivos espalhados e tarefas simples virando mini-expedições.

2) Evolução para WSL como padrão

Com o WSL maduro, ficou possível manter shell, build e automações no Linux sem abrir mão do conforto do Windows para documentação, navegação e multitarefa. Em vez de escolher um lado, você ganha os dois no mesmo fluxo.

3) Fluxo atual de trabalho

  • Código e automações rodam no ambiente Linux (WSL).
  • Edição e navegação acontecem com interface principal no Windows.
  • Repositório e scripts seguem padrão Linux para reduzir variação entre ambientes.
  • Validações finais são feitas em browser desktop e mobile antes de publicar.

5) Como abrir o VS Code no WSL

Dá para abrir o VS Code direto no WSL e manter editor, terminal e arquivos no mesmo contexto Linux do projeto. Na prática, você roda code . no terminal e pronto: o VS Code sobe conectado na distribuição. Se o comando não aparecer, normalmente basta instalar o VS Code no Windows com a extensão WSL (Remote - WSL) que tudo se acerta.

Por que isso é fundamental

  • Consistência de ambiente: desenvolvimento, build e execução acontecem no mesmo Linux.
  • Menos erros de path e permissões: scripts, git, Docker e kubectl seguem o mesmo padrão Unix.
  • Mais performance de I/O: editar no filesystem Linux evita atritos comuns de integração.
  • Fluxo cloud-native real: AWS, Azure, OCI e Kubernetes ficam no contexto correto desde o início.

6) Boas práticas e limites

  • Uso WSL para desenvolvimento, automação e consistência de ambiente.
  • Uso Windows nativo para ferramentas de escritório e comunicação.
  • Evito misturar caminhos e permissões sem critério entre os dois mundos.
  • Mantenho scripts e processos padronizados para facilitar onboarding e reprodução.

7) Conclusão

A história foi mais ou menos assim: primeiro, a gente aprendeu a conviver com dois mundos. Windows para o dia a dia, Linux para desenvolver com previsibilidade. O dual boot segurou essa ponte por anos e foi essencial em muita fase da carreira. Só que ele sempre vinha com uma pegadinha: toda vez que o trabalho atravessava de um lado para o outro, vinha junto um reinício, uma pausa e aquela quebra de ritmo nada charmosa. Quando o WSL amadureceu, essa novela ganhou final feliz. O Linux passou a viver dentro do Windows de forma confiável, o terminal ficou no lugar certo, o editor ficou no lugar certo, e o contexto finalmente parou de fugir no meio da tarefa. O que antes era esforço para manter ambiente virou energia para construir produto.

Dual boot foi heróico no seu tempo, principalmente entre o fim dos anos 2000 e boa parte da década de 2010: dois sistemas, muito contexto e alguns reinícios existenciais. Hoje o roteiro mudou. Com WSL, o Linux roda dentro do Windows sem cerimônia, sem troca de SO e sem a clássica loteria da partição. Resultado: menos novela de ambiente e mais código chegando em produção.
